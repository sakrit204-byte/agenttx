# P3 journal

## 2026-09-16 --- P3-02..P3-05 verified; the outbound path is intercepted

Five BPF LSM programs attached in the guest, verified, and firing:
`file_open`, `path_unlink`, `bprm_check_security`, `socket_connect`,
`socket_sendmsg`.

**The end-to-end number that matters:**

```
syscalls seen        541      every process on the machine
inside a tx           23      what the gate let through
WAL records           23
DROPPED (ring full)    0
```

518 syscalls ignored. That ratio is the design: the hooks fire for
everything on the host, and the first thing each one does is ask
`bpf_tx_current_id()` and return. One RCU bucket walk is the entire cost
for every non-transacting process on the machine.

And the record the project exists for:

```
seq=76  tx=1  socket_connect  reversible   allow  -> 1.1.1.1:80
seq=77  tx=1  socket_sendmsg  compensable  allow  -> 1.1.1.1:80
```

An agent's outbound send, intercepted in the kernel, attributed to a
transaction, classified, and recorded --- with the destination extracted
in-kernel from `sk->__sk_common`.

### Three toolchain traps, each of which produces a misleading error

**`vmlinux.h` must come from the GUEST kernel.** The host runs 7.0 and the
guest runs 6.12. A CO-RE program compiled against the wrong one fails to
load with a relocation error naming a *field*, which sends you looking at
your struct access instead of at your build. The Makefile generates it from
`$(KBUILD_OUT)/vmlinux` --- the kernel we actually boot --- and never from
the host's `/sys/kernel/btf/vmlinux`. Regenerate after every `make vm-kernel`.

**`bpftool gen object $@ $@` truncates the object.** It reads and writes the
same path. The error is *"failed to get ELF header"*, which names the file
rather than the in-place write. That step is for linking several BPF objects
into one; with a single source it is not needed at all, and it is gone.

**`vmlinux.h` has no `#define`s.** BTF describes types, not preprocessor
symbols, so `AF_INET` is simply absent and the error is
`use of undeclared identifier`. The handful of constants needed are restated
at the top of `agenttx.bpf.c`, kept deliberately short: each one is a value
that could drift from the kernel's without anything noticing.

### The silent failure the tests guard against

If `bpf` is missing from the active LSM list, the programs **attach
successfully and never fire**. Nothing errors. `tests/p3/lib.sh` checks
`/sys/kernel/security/lsm` before anything else and skips with that reason,
and `txload` refuses to start without it.

### What is deliberately NOT done yet

`socket_sendmsg` **observes**. It does not defer.

Returning success to userspace for a packet that was never sent is the most
delicate behaviour in the system, and it belongs in its own fragment
(P3-08) with its own test --- not arriving as a side effect of the hook that
first learned how to read a destination address.

For the same reason the class on an outbound send is left at `compensable`
with confidence 0 rather than `reversible`. Claiming a send is reversible is
exactly the thing this project has not yet measured, and
`tx_class_final()`'s fail-closed rule will read that confidence.

## 2026-09-16 (later) --- P3-08: deferral works

`tests/p3/t07_defer.sh`, 9 assertions, all passing:

```
the agent's sendto() reported SUCCESS    15 bytes, no error
the packet did NOT reach the peer        held back while the control arrived
WAL records it as deferred               class=deferrable verdict=deferred
egress actually dropped packets          1 packet(s) never left
```

An agent's fire-and-forget send was held inside the kernel, the agent was
told it succeeded, and nothing reached the peer. On abort it is discarded
and it never existed.

### The architectural finding: an LSM hook cannot defer

`security_socket_sendmsg()` returns allow-or-deny and has no third answer.
Return 0 and the packet leaves; return an errno and userspace sees the
failure. **Deferral is not expressible at the LSM layer at all.** It needs
two interception points: the syscall reports success, and something
downstream of the syscall return suppresses the emission.

That is why this fragment needed `CONFIG_CGROUP_BPF` / `CONFIG_NET_XGRESS`
added to `tools/vm/kernel-common.config`, and why `build-kernel.sh` now
refuses to build without them.

### cgroup_skb/egress drops the packet AND tells the sender

The first working version suppressed correctly and failed anyway:

```
PermissionError: [Errno 1] Operation not permitted
```

`cgroup_skb/egress` returning 0 makes `__cgroup_bpf_run_filter_skb()` return
`-EPERM`, which propagates up `ip_output` → `udp_send_skb` → `udp_sendmsg`
to userspace. The packet was suppressed **and the agent was told**, which is
the one outcome worse than not suppressing it.

`tcx/egress` with `TC_ACT_SHOT` drops inside `__dev_queue_xmit`, which
returns `NET_XMIT_DROP`; `net_xmit_errno()` maps that to `-ENOBUFS`; and
`net/ipv4/udp.c:986` converts `-ENOBUFS` to `err = 0` for any socket without
`IP_RECVERR`. So `sendto()` returns the byte count.

**The mechanism works because the kernel already has a notion of "the packet
went away and the sender does not need to know"** --- it is how a full
transmit queue behaves. Deferral is that, made deliberate.

**The bound this puts on the contribution:** transparency here is a property
of *datagram* semantics. A TCP send suppressed this way is retransmitted and
eventually errors the connection, so TCP deferral needs a different
mechanism and a bounded window. `classify()` therefore does not defer TCP,
and our own gate measurement (18 of 19 connections read a reply back) says
most agent TCP traffic is request-response anyway.

### Two keying bugs, both found by tracing rather than reading

**The socket cookie is useless here.** `sk->sk_cookie` is assigned lazily by
`sock_gen_cookie()`, so the LSM hook --- which runs first --- reads 0.

**`__sk_buff->remote_ip4` is 0 for an unconnected UDP send.** It is filled
from the socket's *connected* peer, and a `sendto()` has none: the
destination came from `msg_name` and exists only in the IP header the kernel
then builds. Traced directly:

```
DEFER write d=100007f dp=19999 proto=17     <- the LSM hook
EGRESS      d=0       dp=0                  <- the egress program
```

So egress parses the packet headers, with
`bpf_skb_load_bytes_relative(..., BPF_HDR_START_NET)` --- relative to the
network header, because `skb->data` starts at L2 on some devices and L3 on
others, and hardcoding either silently parses garbage on the rest.

**An unconnected UDP socket also has no source port at LSM time** ---
`sendto()` auto-binds *during* the send, after the hook returns. So a send
with no source port yet is keyed on `(daddr, dport, proto)` alone.

### Known over-suppression, and the fix

The destination-only key cannot distinguish two processes sending to the
same destination. While a transaction defers to `10.0.0.1:514`, another
process's packets to `10.0.0.1:514` are dropped too.

The fix is not a better key: it is to attach egress to the **agent's own
cgroup or netns** rather than every interface, so it never sees anyone
else's traffic. The tests attach broadly because the guest has no per-agent
cgroup yet. This is a follow-up fragment, not a detail.

### A contract gap found on the way

`struct tx_wal_rec` has no field for `msg_flags`, yet `enum tx_feature_idx`
has `TX_FEAT_MSG_FLAGS` and calls `MSG_DONTWAIT` "the f-and-f signal". The
classifier is specified to use a value the WAL cannot record. An earlier
version smuggled it through `payload_trunc`, which is worse than the gap ---
it corrupted a field that now means something. **Contract-change candidate.**

## 2026-09-16 (later still) --- P3-09: the send arrives iff the transaction commits

`tests/p3/t08_flush.sh`, 9 assertions. Both halves against the same path:

```
abort:  the peer NEVER receives it     the send never happened
commit: the peer DOES receive it       delivered on commit, not before
```

Either half alone proves nothing. "Abort → never arrives" also passes if
suppression is stuck on; "commit → arrives" also passes if suppression never
worked. Only the pair distinguishes deferral from a broken network and from
doing nothing at all.

### Replay is in userspace, and that is not a shortcut

The suppression state lives in BPF maps, which are managed from userspace,
and transmitting a captured datagram from kernel context would mean building
`sk_buff`s by hand for no benefit over a socket. The supervisor is already
the process that decides to commit; it is the right place to make the
decision real.

### The ordering bug that would have made commit a silent no-op

**Suppression must be cleared BEFORE the replay is sent.**

Deferred UDP is keyed on `(daddr, dport, proto)` --- the destination-only
fallback, because an unconnected socket has no source port when the LSM hook
runs. A replay from a fresh socket therefore matches that key just as well as
the original did. Replaying first would mean the commit path emitted a packet
and then dropped it with its own rule: commit would report success and
deliver nothing, and every test that only checked "did commit succeed" would
pass.

`defer_finish()` clears, then sends. The comment above it says why, because
the correct order looks arbitrary until you know what the wrong one does.

### And the commit sequence, end to end

`txctl` runs the effect flush **after** `TX_IOC_COMMIT` returns, not before.
`src/core/commit.c` orders commit fs-then-effects: the undoable half first,
the irreversible half last. Replaying the deferred packets *is* the
irreversible half, so it must not happen until the filesystem merge has
succeeded --- otherwise a failed merge leaves packets on the wire for a
transaction that did not commit, which is exactly the partial commit the
ordering exists to prevent.

Replay order is the contract's: `include/agenttx.h` says `seq` is per-tx,
gap-free, and "defines replay order". An agent that wrote a log line before
sending a notification meant them in that order, and a commit that reorders
them has changed what the transaction did.

### Still open

The control channel is a file per request under `/run/agenttx` --- the
dumbest thing that works, chosen because the maps are not pinned yet and a
socket protocol would be a second thing to debug when the first breaks. Once
the maps are pinned to `TX_PIN_DIR` (the contract already names the paths)
the supervisor can do this itself and the channel disappears.
