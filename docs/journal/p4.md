# P4 journal

## 2026-09-15 --- the gate ran in week 1, and it does not say what it looks like it says

`docs/STATUS.md` section 7 item 4 asks for the gate in week 1 because it needs
no kernel and it decides whether Contribution 1 survives. Ran it on the first
Linux host, against a real agent rather than a fixture.

**Subject.** Claude Code 2.1.272, non-interactive (`claude -p`), asked to read
two files in this repo and summarise them. One run. Captured with:

```
strace -f -tt -yy -s 64 -e trace=network,desc -o run01.strace claude -p "..."
```

13 414 syscalls; `measure_gate.py` parsed 9 644 of them.
Raw trace: `data/gate/run01-claude-code.strace.gz`
Records:   `data/gate/run01-claude-code.jsonl`

**What the tool reported.**

```
outbound socket operations: 46
fire-and-forget    33   71.7%     GATE: PASS (>20%)
request-response   12   26.1%
undetermined        1    2.2%
```

**Why that number is wrong.** The 33 fire-and-forget operations all went to a
single host (the model API, :443) and their payload lengths are

```
64 x6, 331, 398, 417, 422, 459, 472, 576, 599, 642, 644, 820, 1108,
1478 x6, 1504 x3, 1510 x2, 1749, 3511, 20044, 38215
```

The repeated 1478 / 1504 / 1510 are MTU-sized TLS records. These are not 33
independent effects; they are a few *logical* HTTP requests fragmented across
many `sendto` calls. `measure_gate.py` defines "awaits a reply" per syscall, so
a request whose body takes ten `sendto` calls and then blocks on the response
scores as nine fire-and-forget plus one request-response.

The error inflates the headline **in our own favour**, which is the specific
failure mode STATUS.md section 6 is about.

**Re-measured at connection granularity** (group by (pid, fd, peer); a
connection that ever received bytes is request-response in its entirety):

```
connections                19
fire-and-forget             1    5.3%
request-response           18   94.7%
outbound ops on f-and-f connections   1 of 46   2.1%
```

The single fire-and-forget connection sent 1495 bytes and read nothing --
consistent with telemetry.

**Where the truth is.** Neither figure is publishable.

* per-syscall (71.7%) is too generous: it counts TLS fragments as effects.
* per-connection (5.3%) is too harsh: a persistent HTTP/2 connection carrying
  a blocking request *and* a fire-and-forget ping is scored entirely
  request-response.

The honest unit is the **logical request**, which the tool does not model. The
real figure is bracketed by these two and nothing narrower can be claimed yet.

**Consequences.**

1. `measure_gate.py` needs a request-correlation layer before its output is
   evidence. Counting an effect must not depend on how the TLS layer chose to
   fragment it. This is a new fragment, P4-02b.
2. One run of one agent on one task is not the measurement either. The gate
   needs several agents and several task shapes -- in particular tasks that
   send webhooks, notifications and posts, which is where fire-and-forget
   should actually live. This run (read two files, summarise) has almost no
   reason to emit one.
3. Do not quote 71.7% anywhere. If it reaches a slide it will be wrong in the
   direction that flatters us, and a reviewer who reruns it will find the
   fragmentation in an afternoon.

**Not yet known.** 3 770 of 13 414 lines did not parse. Unfinished/resumed
pairs across threads are the likely cause and they are exactly where a blocking
read would appear, so the parse gap is not obviously neutral. Quantify before
trusting either number.

## 2026-09-17 --- the gate, measured properly: ~3%, and it FAILS

Five traces, four task shapes, zero unaccounted lines. See
`docs/gate-result.md` for the full write-up.

```
                     per syscall   per logical request   per connection
  mean                    53.9%                  2.9%             2.2%
```

`PROPOSAL.md`: **< 10% → Contribution 1's ceiling is this number.**

### Two of my own errors, both inflating the result

**Discarding 34-66% of every trace.** The tool skipped `<unfinished ...>` /
`<... resumed>` pairs. That dropped **1571 inbound operations** across four
captures --- replies we never saw, so their sends looked unanswered. Stitching
them (exact: every unfinished call has its resumption in these traces) moved
the figure from 6.3% to 2.9%.

**Negative line accounting.** The first version double-counted stitched
syscalls and printed `UNACCOUNTED -1859 (-13.9%)`. Caught immediately,
because the accounting is printed and has to sum to 100%. That check exists
precisely so a gap cannot hide, and the first thing it caught was mine.

Both errors pushed the number up. Every refinement so far has moved it down.

### What changes

Nothing about the mechanism, which works and is tested. What changes is the
claim. Contribution 1 gets its ceiling stated alongside it; Contribution 5
becomes the headline, as PROPOSAL.md said it might.

The **unit-dependence is itself a result**: a 24x spread between two
defensible definitions of "one outbound effect" means any paper reporting
this fraction without naming its unit cannot be checked.
