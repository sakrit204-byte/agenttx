### The split: userspace mounts, the kernel transacts

`do_add_mount()` is not exported to modules. `fs_context_for_mount`,
`vfs_parse_fs_string`, `vfs_get_tree` and `vfs_create_mount` all are --- so a
module can *build* an overlay superblock and cannot *graft* it into a
namespace. There is no way around that short of a kernel patch.

So the supervisor mounts, in a private mount namespace it unshares itself,
and the kernel owns discard, merge, write-set and external-modification
detection. That is not a concession: it is how every container runtime works,
and "the agent's private mount namespace" in PROPOSAL.md *is* a userspace
unshare. Everything that is actually transactional is in `src/fs/`.

The lower directory reaches the kernel as a **symlink** at
`<tx_root>/tx-<id>/lower`. `struct tx_begin_arg` carries no path and adding
one is a contract-change PR needing four approvals; a symlink costs nothing
and needs none.

### Three bugs worth recording

**1. `opaque` is not `replaced`.** overlayfs marks *every* directory it
creates in the upper layer as opaque, so lookups inside it do not fall
through. The first merge treated opaque as "the agent replaced this
directory wholesale" and refused --- which broke an ordinary `mkdir -p a/b`
inside a transaction, about as common an operation as exists. The
distinguishing test is whether a counterpart exists in the *lower* layer:

* opaque **and** lower exists → wholesale replacement; drop the lower
  contents first or the merge resurrects files the agent deleted.
* opaque **and** no lower → just a new directory; merge normally.

**2. Commit left the CoW area full.** The merge moves regular files down with
`rename()`, but directories cannot be renamed onto existing ones and spent
whiteouts have already been consumed. So a "successful" commit left `upper/`
populated --- costing disk, and making "is `upper/` empty?" useless as a
statement about whether the transaction finished. Now drained, **on success
only**: after a failed merge the upper layer is the only record of what a
partial commit left behind, and discarding it would destroy the evidence.

**3. `iterate_dir()` holds `i_rwsem` for the whole walk.** Calling
`vfs_unlink()` from inside the filldir actor deadlocks against it, and
presents as a hang rather than as a bug. Every walk here collects names
first, finishes the iteration, and only then mutates.

### Two bounds that are not decoration

**Recursion is capped at 32.** The kernel stack is 16 KiB. An agent that runs
`mkdir -p` to 10 000 levels inside a transaction would otherwise overflow it
*during its own rollback* --- a denial of service reachable with one ordinary
command. Hitting the cap fails the abort loudly rather than leaving the upper
layer half-discarded.

**Removal is two passes, not one.** Subdirectories are emptied first while
holding no ancestor's lock, so every mutation happens with exactly one inode
lock held --- its own parent's. A single recursive pass would hold every
ancestor lock at the deepest point, making the depth bound a lock-nesting
bound too, and lockdep would rightly object.

### What is NOT claimed

The merge is **not atomic**. It is a sequence of renames and a crash midway
leaves the lower layer half-updated. P2-09 is that fragment. Until it lands
the honest statement is: atomic *visibility* of effects (the WAL holds them
until commit), non-atomic durability of files.

`upper/` and `lower/` must share a filesystem. A cross-device merge returns
`-EXDEV` and is reported rather than silently becoming a copy --- a copy has
different cost, different atomicity and different inode identity, and a
commit that quietly became one is a commit whose semantics changed without
anyone deciding.
