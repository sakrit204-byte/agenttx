## 4. Three findings worth acting on

**The tree is beating the MLP where it matters.** P4-10 lists the quantised
decision tree as the *fallback* if the verifier rejects the MLP forward pass. On
this data the tree has higher irrevocable recall (0.978 vs 0.889 after int8) and
escalates a third as often, while being a bounded walk over integer comparisons —
which is what eBPF actually wants. Worth entering phase 3 expecting the tree to
be the primary and the MLP to be the comparison.

**int8 quantisation cost 10 irrevocable detections.** Float MLP caught every
irrevocable effect in the held-out set; int8 missed 10 of 90. That is a safety
regression, not a rounding error, and `quantize.py` says so in as many words.
Either `TX_CONFIDENCE_MIN` rises or the tree ships. This is exactly the
"report accuracy lost" that P4-08 calls half the headline figure — it is just
larger than one would hope.

**The class balance is 95/2/1/2.** Raw accuracy is meaningless here; predicting
"reversible" unconditionally scores 95%. Every tool in the pipeline reports
balanced accuracy and irrevocable recall instead, and `train.py` prints
`ignore this` next to the accuracy figure. P4-05's labelling effort should plan
for the imbalance rather than discover it.

## 5. What these numbers are not

Every trace is synthetic, generated by rules we wrote, and every record carries
`label_source="synth"`. A model scoring well against them has recovered
`synth.py`'s own labelling function. `train.py` prints a ten-line banner saying
so, and `features.py --exclude-synth` exists to drop them the moment real
captures arrive.

The only honest claim available from this data is **the pipeline runs end to
end**, which is precisely what P4-04 exists to establish.

## 6. Two tests that were wrong, and why that is in this document

`tests/p4/t06_weights.sh` checks that Python and C agree about the model blob
layout. It passed on its first write. It was also, at that point, nearly useless,
and WORKFLOW.md §5 item 7 is the reason we found out:

> Reviewer sabotages one line and re-runs. A test that passes on broken code is
> worse than no test.

- **First version** compared a C reader against a second Python reader. Both used
  the correct struct definition, so a wrongly-encoded blob was misread
  *identically* by both. They agreed with each other and with nothing real. Fixed
  by comparing against the exporter's declared intent, computed from the source
  arrays before packing.
- **Second version** carried plain sums of the weight arrays. A sum is invariant
  under permutation, so transposing `w1` — 481 changed bytes, every weight in the
  wrong place — produced an identical checksum and passed. Fixed with FNV-1a
  walked in struct index order.
- **The sabotage harness then lied too.** `tests/p4/t06_sabotage.sh` reported
  "10 detected, 0 missed" when in fact the exporter could not run at all (no
  numpy), so every sabotage produced no blob and was scored as caught. It now
  runs a control case first and refuses to report anything if the unmodified
  exporter does not reproduce the reference byte for byte.

Current state: control passes, **8 real breakages detected, 0 missed**, and 2
edits correctly identified as byte-level no-ops. `measure_gate.py` had its own
version of the same disease — a regex that truncated at the `>` inside `->`, so
every reported destination was the *local* endpoint while the headline fraction
stayed right. `tests/p4/t01_gate.sh` now asserts against a hand-counted fixture.

This section is here because `docs/journal/p<n>.md` is supposed to collect
exactly this, and because the same failure — *a check that cannot distinguish
"correct" from "never ran"* — is going to recur in kernel tests, where it is much
harder to see.
